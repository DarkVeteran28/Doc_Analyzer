Why the change was made:
- Hybrid retrieval requires a clear architecture before BM25 scoring,
  diagnostics, and pipeline integration in later checkpoints.

Hybrid retrieval architecture:
- Ingestion remains shared: PDF -> chunk_pages -> identical chunk records.
- Each chunk carries page, local chunk_id (page_N_chunk_M), and text.
- Vector path (unchanged): chunk text -> MiniLM embedding -> ChromaDB,
  keyed by stable id {document_id}_{page}_{chunk_number} with metadata
  document_id, page, chunk_id.
- BM25 path (new): same chunks -> BM25Index.add_chunks, persisted as one
  JSON file per document under bm25_index/ (separate from chroma_db/).
- Stable chunk_id is shared across both stores so fusion can deduplicate.
- Retrieval modes planned for later checkpoints: vector, bm25, hybrid.
- Hybrid default (Checkpoint 5): run vector and BM25 retrieval independently,
  fuse with RRF in rag/fusion.py, pass fused chunks to existing generation.

BM25 module design (rag/bm25.py):
- BM25Index(persist_directory="bm25_index")
- add_chunks(chunks, document_id) stores document_id, chunk_id, page, text,
  and tokenized text per chunk.
- query(document_id, question, n_results) defines the retrieval interface;
  BM25 scoring with rank-bm25 is implemented in Checkpoint 2.
- Persistence is file-based and document-scoped, not stored in ChromaDB.

Fusion module design (rag/fusion.py):
- reciprocal_rank_fusion(ranked_lists, k=60) merges ranked result lists.
- Deduplication uses stable chunk_id.
- Metadata (page, text, document_id) is preserved from the first occurrence.
- Ranking is deterministic: RRF score descending, then chunk_id ascending.

Public interface preservation:
- rag_service.process_document(...) and rag_service.ask_question(...) signatures
  remain unchanged through this checkpoint.

Why the change was made:
- BM25 keyword retrieval is required for hybrid fusion and must index the
  same chunks as the vector store while remaining document-scoped.

BM25 implementation details:
- add_chunks persists one JSON file per document under bm25_index/.
- Each record stores document_id, chunk_id, page, text, and tokenized text.
- query tokenizes the question, builds BM25Okapi from the document corpus,
  ranks by score with chunk_id tie-breaking, and returns top n_results.
- Stable chunk_id format matches ChromaDB: {document_id}_{page}_{chunk_number}.
